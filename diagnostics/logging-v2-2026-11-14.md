The conversation-update warning itself is still unreproduced on our owned emulator conversation. This change repairs evidence collection and adds a way to locate its renderer; it is not a stable application fix.

## Reproduced logging defect

The reporter's first report showed1356 dropped observations. To reproduce the mechanism deterministically, the same-key API31 instrumentation pauses the real capture worker, submits5000 metadata observations, then submits a conversation turn, stream frame, capabilities, request version and native RobinStatus1086 before releasing the worker and stopping/exporting.

With the published diagnostics1 runtime, the report loses the turn, stream, capabilities and request version. The native status/classifier survives its separate important queue. The test correctly fails at `validate_burst_retention`; it is not counted as a passing run. With the corrected runtime, all those event kinds survive, process-loss accounting is present and unexpected loss is0. Fake email/URL/conversation-ID/message canaries are absent in both exported reports. This is a logging regression fixture, not reproduction of the reporter's conversation warning.

`CaptureInbox` gives repeated snapshot kinds up to four pending entries (first three plus latest), instead of letting history consume a shared24-entry queue. Turns and real status details retain separate bounded admission, and stream/error/warning kinds cannot be displaced by metadata. Overflow remains bounded and explicit. The standalone concurrency test additionally exercises20000 history observations, four producers, latest-snapshot retention, stale-generation rejection and explicit overflow counts.

**Coalescing is deliberate sampling, not a complete raw-message recording.** Intermediate metadata/frame snapshots may be merged and every merge is counted by kind. Do not describe a completed capture as proof that every protobuf was inspected. Unexpected queue/file/budget loss is reported separately.

## Cross-process stop and export

All file-lock waiting occurs on the background worker. Append waits for another process's lock instead of silently dropping that record. Observation timestamps are taken on admission. Stop writes a shared cutoff; queued pre-cutoff work may drain after stop, while later work is excluded. The15-minute deadline is retained.

Each participating process atomically checkpoints its own admission counters, pending count, loss totals and stop acknowledgment. Export includes all process summaries, `allStoppedProcessesAcknowledged`, `minimumObservedLoss` and `incomplete`; it no longer substitutes the UI process's zero counter for every process. Stop/export wait for acknowledgments within a bounded interval. A dead/unacknowledged/missing-summary process or an explicit loss marks the report incomplete. Journal PIDs without a summary are also retained as missing-summary records. Internal generation timestamps are not exported.

## Package inventory defect identified

The actual Android Manager diagnostics1 APK was inspected. Its capture-start array contains the Google clone package **twice**, with no original-Google identity. Manager's extension optimization folded the StringBuilder expressions into literals, then `Google App Package Clone Support` rewrote the original literal. This explains the three keys in the reporter report; it is not evidence that original Google was absent.

The clone rewrite now excludes only our diagnostic namespace. Normal Google code follows the unchanged baseline algorithm. Four distinct inventory identities are preserved and must be checked on the actual Manager-produced APK, not just the Desktop build.

The periodic warning detector additionally records static view/resource/ancestor identifiers. A quoted warning can still match and must be distinguished from the actual warning UI.
